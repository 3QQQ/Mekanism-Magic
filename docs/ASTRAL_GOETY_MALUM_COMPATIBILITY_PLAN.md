# Astral Sorcery、Goety 与 Malum 兼容规划

本项目将 Astral Sorcery、Goety、Malum 纳入后续兼容路线，目标为当前 `main` 分支的
Minecraft 1.21.1 / NeoForge。优先完成依赖与加载预检，再按“精魂灌注 → 诅咒注入与
灵魂吸收 → 聚星与星能注入”的顺序交付可独立验证的机器。这是首批交付顺序；完整范围
还包括符文、修复、魂缚、仪式、坩埚药酿、聚焦转化、流明生产和水晶培育等设备体系，
见下方完整候选清单。

**本文件是后续规划，不属于正式版 1.0.7 的功能。** 三模组后续开发独立保留，
本次正式包精确采用 1.0.6.66 运行代码，不含九台新机。发布范围见 [1.0.7 日志](RELEASE_NOTES_1.0.7.md)。
Forge 1.20.1 分支需要另做版本与 API 审计。

## 单方块设计原则

**默认交付独立单方块机器。** 每台机器本体占一格，GUI、物品槽、液槽、资源缓存、工具、
加工进度与存档集中在本机。运行时尽量不要求玩家再摆原生祭坛、基座、液池、刷怪笼、
方舟、坩埚、圣杯或图腾结构；前版“先做外部原装置控制器，再评估压缩”的路线由本原则替代。

单方块是本附属的设计目标，不代表原模组本来支持这种形态。空间结构可以改造；
配方材料、分类资源、工具损耗、玩家归属、研究与动态结果仍分别适配。接口依赖原生
方块类时编写版本桥接或本机执行计划，不在世界暗放假结构，也不只把名称改成“单方块”。

| 原生要求 | 单方块中的设计 |
| --- | --- |
| 祭坛、基座、图腾与等级结构 | 原装置及结构材料进入机器制作/升级成本；等级、图腾类型、符记组合在机内保存 |
| 刷怪笼等运行位置条件 | 设计可在生存取得的合成资格或功能核心；不要求另放刷怪笼，也不默认消耗生存无法取得的刷怪笼物品 |
| 液池、圣杯和多液交互 | 机内单/双液槽及实际配方液体成本；按原概率决定消耗 |
| 水晶簇与原料在世界中的等待 | 晶种槽、生长阶段、成熟时刻与采收模式；保留真实成本、概率、属性与退化 |
| 方舟、诅咒之笼、蜡烛供能 | 机内对应功能模块及真实图腾/连接宝石、绑定和资源状态；模块本身不凭空生魂 |
| 工具、促符、增强件、原生加速器 | 保留实际物品与组件的专用槽；消耗/耐久/数量上限独立结算，必要的昂贵增益进入升级模块 |
| 夜晚、星座、月相、维度与研究 | 按具体流程在本机位置或真实玩家上检查，不能因压缩结构就自动满足 |
| 玩家、实体、真实世界效果 | 单方块本体执行真实目标操作；目标不是外部机器结构，仍保留权限、范围与原生资格 |

不为每台机器硬造一种通用核心。原装置优先作为制作材料，只有等级、类型选择、绑定或
可更换功能确实需要时才用保留核心槽。新增核心的名称和配方另行设计，不当作原模组官方物品。
四阶祭坛按同一单方块家族逐阶升级，阴咒注入按进阶/工厂扩展，同机模式不重复计算设备数。

### 原则上的少数例外

魂缚需要真实参与者，召唤/转化需要真实实体，定位/传送需要真实目的地，采掘/生长/治疗
需要真实世界目标。这些功能仍使用单方块执行器，不附带原生多方块结构。
物品共鸣可以机内化；玩家共鸣选择、星能力操作、遗物解谜及玩家传送保留主动交互。
如个别桥接暂时不能实现机内化，列为该功能的待实现项，不默认降级成交付外部控制器。

## 原生规则审计与单方块适配

本节记录原生机制，外部结构条件不直接沿用为本附属的运行要求；它们按上方设计转换。
保留成本、概率、状态和真实对象，与保留原装置摆放形状分别处理。

### Malum

静态定义：精魂灌注 144、释缚嬗变 70、精魂修复 65、魂缚 36、符文工艺 24、
精魂聚焦 14、虚空赐物 13、结点高炉/熔炼各 10。运行时以条件过滤后的 RecipeManager 为准。

SpiritInfusionRecipe.matches 只检查主料和精魂，不检查 extraInputs。本机必须完整匹配辅料。
getOutput(ServerLevel, ItemStack) 保留 carryOverComponentData 与附魔筛选，不能复制固定 result。
原祭坛计时由阶段和残留进度驱动，不是统一固定 300 tick；本机时长另标为设计值或按原流程推导。

SpiritCrucibleCoreBlockEntity.craft 的促符耐久、不稳定性、幸运、增强件与特殊后果转为
本机状态机；碎裂物通过 FRACTURED_IMPETUS_VARIANT 返还，修复时保留 REPAIRED_IMPETUS_VARIANT。
魂缚结果为 GeasEffectType，作用真实玩家/生物并保留献血与失败伤害，不能伪造离线参与者。
哭泣之井可机内化反应，但队列、无效物返回和特殊黏物连续投喂仍须持久保存。
SoulHarvestHandler 的无魂、刷怪笼配置、掉落事件与已收割标记不因单方块而取消。

不使用 FakePlayer。当前样本耗空图腾会消耗图腾，与书籍概述不同，须按基线验收。
亡灵火炉保留深暗之域、实际供魂与中断损失；书籍与移植代码的笼子条件差异另做对照验证。

RitualRecipe 的普通 matches 固定 false、assemble 固定空，不能把全部仪式当普通合成。
祭坛流程中的按秒魂耗、真实玩家、研究、附魔等级和完成回调需要机内执行计划。
pulverize 有 136 条仅方块结果、6 条方块兼物品、22 条仅物品；逐类支持真实结果。

### Astral Sorcery

静态定义：祭坛 94、流明结晶 27、星能液交互 15、流明生成 14、聚焦转化 11、
聚焦合成 9、聚星缸 9、液体交互 6、星能注入 3，不能套用旧版玩法。

TileLightwell 的水晶属性、生产倍率、随机取整和碎裂在机内重现，不改成固定无限产液。
其外部上方阻挡条件是原装置空间规则，单方块凝液器按内部有效催化物状态设计；
不为它新增原本没有的夜晚/星能束输入要求。

InfusionRecipe 的概率耗液、多个同配方液源的消耗和圣杯供液许可改为内部液槽与可接受的输入方式。
原注入器需要外部结构，本附属由制作成本替代；它本来没有额外昼夜或屋顶条件。

LumenCrystallizationRecipe.consumeInputs/createOutput 抛 UnsupportedOperationException，
实际生长在 TileLumenCrystallizer。结晶舱必须迁移完整维护、成簇、成长、成熟与催化物状态，
不能只把 27 条配方转为固定输出。天辉矿基座改内部催化槽，退化照原概率结算；
曜变宝石保留真实最终成熟时刻与过熟退级。

祭坛 output_modifiers 包含研究提升、放置/升级祭坛、组件/属性处理与随机结果。
其中本附属祭坛升级走本机升级流程，研究提升校验实际玩家；不能照搬依赖 TileAltar 的方法。
原生事件若强依赖原方块实体，优先提供可取消的附属加工事件，能够正确适配时再桥接原事件，
不伪造原装置来声称事件兼容；逐项记录其他附属可观察到的行为差异。

工厂按活跃工位计费，速度升级不自动绕过天象、研究或按时结算条件。

## 项目接入与结算边界

三模组分别建立 integration/astralsorcery、integration/goety、integration/malum 模块，
经 ModCompatibility 与 IntegrationBootstrap 独立门控，第三方类不进入通用机器循环。
普通物品结果可转换为 MachineRecipeResult；需要多阶段、动态资源、世界或玩家效果的
单方块机器使用专用可持久化执行计划。配方目录保留动态解析入口，准备加工时用真实主料组装结果。

机内事务先完整检查和模拟材料、资源、输出，再提交并保存待产物。概率、工具损耗和成长阶段
保存到本机，正常保存/重启、堵塞、拆机不得重抽或重复扣费。世界效果另外检查真实目标、
权限与失败边界，不以虚拟结构取代世界操作，也不假定原生方法必定无副作用。

SEHelper 是 void 且带事件，没有 simulate、确认量或幂等事务 ID。单方块吸收器应在服务器
主线程预留输入、一次扣料和调用、防重复请求；不能因余额没变就重试、补写或返料，
因为事件可把增益改为零、改走图腾或触及容量上限。玩家存档与机器 NBT 没有共同原子提交，
必须区分正常保存重启与异常进程终止，不能在尚无账本端幂等适配时承诺跨存档崩溃恰好一次。
此前不做异步并行、离线补记；无法保证的细分功能保留待验证状态，不以外接方舟规避问题。

配方快照在成功全局重载后刷新，旧 ID 签名不匹配时清理上下文；登录/开 GUI 不扫描全表。
版本与哈希锁定，第三方 JAR 不入包。已有库存机器不能因不支持版本静默省略注册。
当前共享管道的 MagicPipeResourceHooks 仍是单一工厂入口，扩展资源前须改可组合注册，
并检查 magicPipesEnabled、MagicResourceKeys、显示/磁盘/缺失依赖恢复；该重构不阻塞
首批单方块的真实物品/流体物流，也不据此给所有资源强造统一管道。

## 实施顺序与验收

| 阶段 | 单方块交付 | 验收重点 |
| --- | --- | --- |
| 0 依赖预检 | 解决样本声明与依赖，锁定正常上游构建 | 标准客户端与专用服务器加载，不改原 JAR 或跳版本检查 |
| 1 基础模块 | 版本门控、配方目录、本机核心/模块与阶段数据设计 | 入口独立，加载条件过滤，实时条件在 JEI 显示未满足原因 |
| 2 精魂加工 | 精魂灌注舱，再扩符文与修复 | 单方块完整辅料、分类精魂与动态组件 |
| 3 诅咒与灵魂 | 注入、吸收与修补 | 无外置刷怪笼/方舟/笼结构，取得门槛可生存达成，真实归属与能源结算 |
| 4 聚星与注入 | 独立凝液器、注入舱 | 无原聚星缸/外部液池；概率、流体成本、取消行为和持久状态正确 |
| 5 常规扩展 | 聚焦、坩埚、火炉、流明、结晶、四阶合成、反应、基础凿刻 | 独立机体；原结构成本机内化，生长与资源阶段可保存 |
| 6 世界与仪式 | 魂缚、嬗变、虚空赐物、仪式、药酿、共鸣、培育、树木等 | 机体单方块，真实目标和参与者；无隐藏假结构/原装置依赖 |
| 7 工厂与网络 | 阴咒进阶、工厂、Extras、AE/MekE 与合格资源通道 | 各工位独立费用，动态/世界结果逐类支持，升级保持机体单方块 |

阶段 2—4 可按正常样本并行推进。每台机器要在不摆原装置/原结构的独立测试场景完成工作，
并覆盖输出满、红石、升级、原料抽走、重载、区块卸载、正常重启、拆机与还原。
世界模式覆盖目标变化、主人离线、权限拒绝和不可用区块，不强制加载世界。
玩家账本等跨持久化状态另列异常进程终止测试与已知边界，不能用正常重启测试代替。

组合矩阵覆盖三个模组单装、两两、三装、全缺失，以及现有魔法模组和 AE2/Extras；
GUI/动画需单独客户端验收。机器实现遵循 [新增机器契约](ADDING_MACHINES.md) 和
[命名约定](MACHINE_NAMING.md)，中英 block/container 与 JEI 同步，共用标题和状态布局。
运行 validateMachineContracts、testMachineTitles 及专用测试；仅实际运行时代码完成并验证后，
才按 [版本规则](VERSIONING.md) 为整轮改动增加一次开发编号。
