# 开发与发布版本规则

版本号唯一来源为 `gradle.properties` 中的 `mod_version`。JAR 文件名、NeoForge 模组信息和游戏内版本均由它生成，不靠改文件名区分构建。

**硬性原则：模组运行时代码未发生新的实质改动，严禁滚动模组版本。**
任务轮数、构建次数、资源包修订次数都不是模组版本递增依据。以下规则按 2026-09-08
的新要求执行，优先于早期“游戏资源改变也自动递增”的约定。

## 编号

| 状态 | 示例 | 递增方式 |
| --- | --- | --- |
| 已发布版本 | `1.0.6` | 保留现有正式版本格式 |
| 第一轮未发布改动 | `1.0.6.1` | 在正式号后追加 `.1` |
| 后续未发布代码改动 | `1.0.6.2`、`1.0.6.3` | 每完成并验证一轮实质运行时代码修改，末尾编号只加一次 |
| 下次正式发布 | `1.0.7` | 正式号的最后一段加一，去掉开发编号 |
| 发布后继续开发 | `1.0.7.1` | 从新正式号后重新追加 `.1` |

这里用户所说的“大版本号”指原有正式版本号整体，不是每次发布都把 `1.x.x` 改为 `2.x.x`。

## 执行规则

- 只有新的、实质性的模组运行时代码改动完成并通过验证，才递增一次开发编号，并说明改动依据。没有实际改代码的需求、仅检查后确认无需修改的任务，不得增号。
- 独立资源包的贴图、配色、文字色表及预览修改，只递增资源包自身版本，不滚动 `mod_version`，不重打模组 JAR。资源包 1.0→1.1→1.2 不得带动模组版本。
- 独立模型、Blockbench 工程与预览使用 V4/V5 等设计编号。代码注释、格式整理、构建/校验工具、文档及版本号纠正不属于模组运行时代码改动，不递增。
- 仅资源、配方或配置发生变化而运行时代码不变时，也不得擅自加模组版本。若必须重打内容不同的模组 JAR，而当前编号已有历史产物，先向用户说明编号冲突并等待明确安排；不得自行滚号或覆盖历史 JAR。
- 同一轮代码修改中的编译、修正、测试和重打包共用一个开发编号。单纯查询、检查、启动客户端或重复构建严禁改号，以保持构建可复现。
- 加号前必须指出相对最后有效代码基线的新运行时代码差异。仅版本元数据变化、独立资源包变化、旧 JAR 改名，均不构成依据；不能先加号再用新编号反过来证明有改动。
- 本规则启用时，未发布自然灵气适配统一编号为 `1.0.6.1`；不再使用 `1.0.6-dev-nature-...` 之类临时版本覆盖。
- 正式发布需用户明确要求。先将源码版本更新为下一正式号，构建和核验，再以同一号创建标签、GitHub Release 和 CurseForge 文件。
- 1.21.1 正式标签使用 `v1.0.7-neoforge-1.21.1` 这类格式。CurseForge 发布流程会拒绝四段开发号或临时后缀；版本格式检查单独放行已存在的 `1.0.5fix`，但不跳过其他发布包校验，也不表示当前流程能够重发所有历史包。
- 比较开发版本时按数字段排序：`1.0.6.10` 晚于 `1.0.6.2`，不能按普通字符串排序。正式发布必须前进到 `1.0.7`，不能只删除开发段退回 `1.0.6`。
- 不修改旧发布、旧标签或已有测试包；不因更改版本规则自动发布自然灵气适配或改动 1.20.1 分支。

## 旧 1.0.6.39 空增纠正

本次将 `mod_version` 从 `1.0.6.39` 恢复为最后存在实质代码改动的 `1.0.6.38`。

- `.38` 相比 `.37` 增加了可选界面资源包的运行时主题桥接代码，是有效代码版本。
- `.38` 与 `.39` JAR 的 664 个类和包内资源逐项一致，唯一不同的条目是
  `META-INF/neoforge.mods.toml` 中的版本元数据；因此这个旧 `.39` 包不作为新的代码基线。
- AE Terminal 资源包的 1.1、1.2 等独立修订保留，继续由资源包自身编号管理。
- 旧 `.38`、`.39` JAR 不删除、不覆盖；已有正确的 `.38` JAR 可继续使用，无需重打。
  后续真实代码改动若遇到已占用的历史文件名，必须先明确处理编号/归档安排，不能直接覆盖。

本次核验的 `.38` JAR SHA-256：
`4BD0DB7DE81115B31DB94990B46CCCC0D1CF134CF7467D3E1309B81DAE3645E6`。

随后“自然灵气与禁忌界面去除常驻说明”确实修改了界面运行时代码。用户明确选择
“归档旧 .39，使用新的 .39”：旧包移入 `build/libs/withdrawn/`，字节和哈希保持不变；
旧说明保存在 [撤销记录](history/RELEASE_NOTES_1.0.6.39_WITHDRAWN.md)。完成代码与测试后，
才将 `mod_version` 从 `.38` 递增一次到新的 `.39`。新旧同号产物以路径、内容及哈希区分，
不是覆盖旧包或再次进行无代码滚号。

## 独立样机版本纠正

以下为旧规则下的历史记录，不作为今后资源改动自动递增模组版本的依据。

按用户要求，独立设计阶段误用的 `1.0.6.17`—`1.0.6.20` 已撤销，
`mod_version` 恢复为最后实际接入游戏资源并打包的 `1.0.6.16`。
模型、预览及设计记录保留，没有回退游戏代码或删除旧 JAR。原编号的设计记录仅作历史说明，
不表示存在这些版本的游戏构建。之后真正接入新模型时才递增开发号，不能用恢复后的旧号覆盖已有测试包。

当前 V4 模型经用户确认后正式接入，开发版本因此从 `1.0.6.16` 递增为 `1.0.6.17`。
原误用 `.17` 的 V2 设计记录迁移至 `MODEL_DESIGN_NATURE_V2.md`，不与本次实际构建混用。
随后实际接入 Forbidden & Arcanus 基础与容器兼容，递增为 `1.0.6.18`；原误用 `.18` 的 V3
设计记录保留在 `MODEL_DESIGN_NATURE_V3.md`。
第一台禁忌燃烧处理机实际接入后递增为 `1.0.6.19`；早先误用该号的独立V4转换器记录保留在
`MODEL_DESIGN_NATURE_V4_CONVERTER.md`，不与实际运行时日志混用。
自动赫菲斯托斯锻炉第一阶段实际接入后递增为 `1.0.6.20`；原误用该号的独立自然灵气
系列设计记录移至 `MODEL_DESIGN_NATURE_V4_SERIES.md`。新的 `.20` 日志只描述实际代码和测试包。
